# PROMPTS · คลังพรอมต์สั่ง AI สร้างงาน "One-stop" (ต้นทุนวัตถุดิบ + บัญชี)

พรอมต์ทุกตัวในไฟล์นี้เขียนให้ **วางลงใน AI coding agent (Claude Code ฯลฯ) ได้ทันที** เพื่อสร้างส่วนที่ repo นี้ **ยังไม่มี** ตามคู่มือ One-stop (ข้อกำหนดเต็มอยู่ใน [ONESTOP-SPEC.md](ONESTOP-SPEC.md))

## 1. ใช้อย่างไร

1. เปิด session ใหม่ **ต่อ 1 พรอมต์** แล้ววาง "พรอมต์ร่วม" (ข้อ 4) ตามด้วยพรอมต์ที่เลือก
2. ทำตามลำดับ **P1 → P11** (แกนหลัก) พรอมต์ P12–P20 (roadmap) ทำหลังแกนหลักนิ่งและใช้งานจริงแล้ว ห้ามข้าม P2 (สมุดบัญชี) เพราะขั้นหลังพึ่งมัน · P21–P27 มาจากเมนูที่ผู้ใช้ส่งมา (ข้อ 6b) โดย P21 (จัดเมนูเป็นกลุ่ม) ควรทำ **หลัง P1 ก่อน P2** เพื่อให้หน้าจอใหม่ทุกขั้นอยู่ถูกกลุ่มตั้งแต่แรก
3. ทุกพรอมต์สั่งให้ AI **เสนอแผนและถาม "คำถามที่ต้องถามก่อน"** ก่อนเขียนโค้ด ใส่ค่าแนะนำไว้แล้ว ตอบว่า "ตามที่แนะนำ" ได้
4. จบแต่ละขั้น ตรวจรับตามหัวข้อ "ตรวจรับ" และสั่ง Q1–Q3 (ข้อ 7) เป็นระยะ
5. ตัวเลขเรื่องภาษี/บัญชีทุกจุด **ต้องให้ผู้ทำบัญชีตรวจ** (P19) ก่อนใช้จริง

## 5. แกนหลัก P1–P11

### P1 · โครงฐาน: โหมดต้นทุนและบัญชี + บทบาทผู้จัดการ + คิวรออนุมัติ + ค่าตั้งระบบ

````text
งาน P1: วางฐานที่ P2–P11 ต้องใช้ โดยร้านที่ไม่เปิดโหมดใหม่ต้องทำงานเหมือนเดิมทุกอย่าง

สร้าง
1) settings.modes.cost = "ต้นทุนและบัญชี" ค่าเริ่มต้น false: cleanModes()/LEGACY_MODES/POST /api/settings/renderBiz()/lib/biz.js ทุกประเภท · เปิดพร้อม modes.buy ไม่ได้ (400 บอกเหตุผล) · บันทึก settings.costSince (เวลาที่เปิด) สมุดบัญชีเริ่มนับจากตรงนี้ ไม่ลงย้อนหลัง
2) settings.cost = { foodTarget:35, priceRise:10, expenseLimit:3000, wasteAck:500, vatRegistered:true } ช่วงที่ยอมรับ: foodTarget 5–90, priceRise 1–100, expenseLimit/wasteAck 0–1,000,000 บาท · แผง "ต้นทุนและบัญชี" ในตั้งค่า · เจ้าของแก้ได้เท่านั้น · เปลี่ยน expenseLimit/wasteAck/vatRegistered ต้อง requireFresh + audit
3) บทบาท manager ("ผู้จัดการ") ตามคำตอบข้อ 1 ด้านล่าง: ROLES, กลุ่มสิทธิ์ใหม่ MGR, ใส่ manager ใน FRONT และ SERVE (แตะเงินได้) แต่ห้ามจัดการพนักงาน ตั้งค่า สำรอง/กู้คืน MySQL PromptPay แก้เมนู · เงื่อนไข role==='owner' ในอายุ cookie (issue()/staffOf()) ให้ manager ได้อายุแบบเจ้าของ · allowedTabs()/TABS · README/GUIDE ตารางบทบาท
4) เครื่องอนุมัติกลาง: D.approvals [{id, kind, effect:'hold'|'ack', ref, by:{id,name,role}, at, amount, reason, payload, status:'pending'|'approved'|'rejected'|'recount', decidedBy, decidedAt, note, selfApproved?}] · GET /api/approvals · POST /api/approval/decide {id, decision:'approve'|'reject'|'recount', note} สิทธิ์ MGR · เซิร์ฟเวอร์บังคับ "ผู้ตัดสิน ≠ ผู้บันทึก" (ยกเว้นกรณีตามคำตอบข้อ 2 ซึ่งต้องติด selfApproved ใน audit) · kind ลงทะเบียนตัวจัดการ {apply, reject} จาก P5/P6/P7 (พรอมต์นี้ทำเครื่องกลาง + เทสต์ด้วย kind จำลอง) · effect 'hold' = ยังไม่มีผลจนอนุมัติ · 'ack' = มีผลแล้ว แค่ให้ผู้จัดการรับทราบ · รายการที่ตัดสินแล้วเก็บ KEEP_DAYS วัน (audit เก็บถาวร)
5) หน้า "รออนุมัติ" (ตัวเลขบนแท็บ) สำหรับ MGR ใช้ SSE เดิม

คำถามที่ต้องถามก่อน
1. ผู้จัดการ = (ก) บทบาทใหม่ manager สิทธิ์ต่ำกว่าเจ้าของ [แนะนำ] หรือ (ข) ใช้บัญชีพนักงานบทบาท "เจ้าของ" (ทำได้อยู่แล้ว แต่ได้ทุกสิทธิ์รวมตั้งค่า/กู้คืน)
2. ร้านที่มีแค่เจ้าของคนเดียว: รายการ hold ที่เจ้าของบันทึกเองอนุมัติเองได้ไหม [แนะนำ: ได้ ติดป้าย selfApproved ใน audit และรายงานสัปดาห์ เพราะร้านเล็กส่วนใหญ่มีคนเดียว]
3. vatRegistered ซ้ำกับ settings.vat (VAT เริ่มต้นบนบิล) ไหม [แนะนำ: แยกกัน vat = ค่าเริ่มต้นบิลขาย · vatRegistered = ร้านจด VAT แยกภาษีซื้อ/ขายในบัญชี ถ้า false ภาษีซื้อนับเป็นต้นทุน]
4. PIN เจ้าของ approvePin ยกเลิกตั๋ว รับ PIN ผู้จัดการด้วยไหม [แนะนำ: ไม่ คงเดิม]
````

### P4 · สูตรมาตรฐาน + ต้นทุนต่อจาน + ตัดวัตถุดิบตอนขาย



### P6 · รับของ + งบซื้อรายหมวด + เตือนราคาขึ้น + ภาษีซื้อ + เจ้าหนี้


### P7 · รายจ่าย / รายรับอื่น + วงเงินอนุมัติ

````text
งาน P7: บันทึกรายจ่ายและรายรับอื่น ลงสมุดบัญชี พร้อมวงเงินที่ต้องอนุมัติ · ต้องมี P1, P2

5) หน้า บัญชี › บันทึกรายจ่าย/รายรับ: ฟอร์มสั้น (เลือกหมวดเป็นชื่อไทย) ใช้งานบนมือถือได้ รายการวันนี้ ค้นหา · ช่องเลขเอกสาร/ใบเสร็จ

1. วงเงินวัดต่อรายการหรือรวมต่อวัน [แนะนำ: ต่อรายการ ตามคู่มือ] เกิน = มากกว่า (>) [แนะนำ]
````

### P8 · รายงาน: กำไรขาดทุน · ส่วนต่างการใช้ · ภาษีประมาณ · สมุดรายวัน CSV

### P9 · KPI + ภาพรวมธุรกิจ + งานประจำวัน/สัปดาห์/เดือน

````text
งาน P9: หน้า "ภาพรวมธุรกิจ" ของผู้จัดการ: KPI พร้อมสัญญาณเตือน "สิ่งที่ต้องดู" "ควรสั่งซื้อ" และรายการงานที่ระบบรู้เองว่าทำหรือยัง · ต้องมี P1–P8

KPI ตามคู่มือ (ตัวเตือน): Food cost % จริงสูงกว่าเป้า > 3 จุด · ส่วนต่างจริง−สูตร > 2% ของยอดขาย · ของเสียเดือนนี้ > 2–3% ของยอดขาย · งบซื้อรายหมวดใช้ > 90% ก่อนสิ้นเดือน · PromptPay รอยืนยันค้างข้ามวัน · เจ้าหนี้เกินกำหนด · วัตถุดิบติดลบ

4) แจ้งเตือน: ใช้ toast/ป้ายเดิม เสียงตามกฎข้อ 55 เฉพาะเรื่องด่วน (รออนุมัติ) ห้ามรบกวนครัว

คำถามที่ต้องถามก่อน
1. งบ > 90% "ก่อนสิ้นเดือน": [แนะนำ: ใช้ > 90% ขณะที่วันที่ปัจจุบันยังไม่ถึงวันสุดท้ายของเดือน ตามตัวอักษรของคู่มือ]

เสร็จเมื่อ: เปิดร้านแล้วผู้จัดการเห็น "สิ่งที่ต้องดู/ควรสั่งซื้อ" ถูกต้อง ปิดร้านรู้ว่าอะไรยังไม่ทำ
````

### P11 · ยืนยันยอด PromptPay + ปิดกะเงินสด


## 6. Roadmap P12–P20 (ทำหลังแกนหลักใช้งานจริงแล้ว)

### P12 · Lot และวันหมดอายุ (FEFO)

````text
งาน P12: ติดตาม lot และวันหมดอายุของวัตถุดิบ ตัดแบบหมดอายุก่อนตัดก่อน (FEFO) และแจ้งเตือนใกล้หมดอายุ · ต้องมี P3 P6
- ใบรับของใส่ lot (เลข วันหมดอายุ จำนวน) ต่อบรรทัด (ตั้งต่อวัตถุดิบว่า "ติดตามวันหมดอายุ")
- ingMove ขาออกจัดสรรจำนวนเข้า lot ที่หมดอายุก่อน · มูลค่าคงใช้ต้นทุนเฉลี่ยเคลื่อนที่เดิม (lot เก็บ จำนวน+วันหมดอายุเท่านั้น ห้ามเปลี่ยนสูตรมูลค่า) [คำถามข้อ 1: ยืนยัน]
- แจ้งเตือน X วันก่อนหมดอายุ (ตั้งค่าได้) + หมดอายุแล้วเสนอ "บันทึกของเสีย เหตุผลหมดอายุ" ให้ผู้จัดการกดยืนยัน ห้ามตัดเอง
- ΣจำนวนในทุกLot = stock ของวัตถุดิบเสมอ (เทสต์สุ่ม) · ตรวจนับปรับจำนวนจาก lot ที่เก่าก่อน · ยกเลิกใบรับของคืน lot นั้น
- ไฟล์ใหม่ (ถ้ามี) ต้องรวมในสำรอง/กู้คืน/MySQL ตามกฎ
ถามก่อน: 1) มูลค่าตาม lot จริง (FIFO) หรือเฉลี่ย [แนะนำ: เฉลี่ย] 2) วัตถุดิบไหนบังคับใส่วันหมดอายุ
````

### P13 · สูตรย่อ / ของเตรียม

````text
งาน P13: วัตถุดิบที่ผลิตเองจากวัตถุดิบอื่น (น้ำซุป ซอส) ตัดสต็อกตอนเตรียมเป็น batch · ต้องมี P3 P4
- วัตถุดิบชนิด "ของเตรียม" มีสูตรย่อ + ปริมาณผลผลิตต่อ batch · POST /api/prep {ing, batches} ตัดวัตถุดิบดิบ (ingMove 'prep') เพิ่มของเตรียม มูลค่าที่เข้า = มูลค่าที่ตัดออกรวมกัน (โอนมูลค่าภายใน 1200 ไม่กระทบ P&L) ทุนเฉลี่ยของเตรียม = มูลค่า ÷ ปริมาณผลผลิต
- เสียระหว่างเตรียม = ผลผลิตจริงน้อยกว่าที่ควร: ผู้ใช้ใส่ผลผลิตจริง ส่วนต่างบันทึกเป็นของเสีย (5100)
- สูตรเมนูใช้ของเตรียมเป็นวัตถุดิบได้ (ซ้อนได้ไม่เกิน 3 ชั้น ห้ามวนกลับ ตรวจรอบก่อนบันทึก) ต้นทุนต่อจานแตกลงถึงวัตถุดิบดิบ
- เทสต์: ต้นทุนซ้อนชั้นตรงแบบจำลอง · รอบวนถูกปฏิเสธ · 1200 ตรง · kill -9
ถามก่อน: 1) ขายหน้าร้านตัดของเตรียมทันที หรือตัดดิบตอนเตรียมเท่านั้น [แนะนำ: ตัดของเตรียมตอนขาย ดิบตอนเตรียม]
````

### P14 · ค่าธรรมเนียมบัตร + แพลตฟอร์มเดลิเวอรี

````text
งาน P14: วิธีชำระใหม่ บัตร (EDC) และแพลตฟอร์มเดลิเวอรี พร้อมคำนวณค่าธรรมเนียมอัตโนมัติ · ต้องมี P2 P7 P11
- ตอนนี้ method มีแค่ cash|transfer กระจายอยู่ทั่ว (normalize sales, POST /api/pay /api/sale /api/doc/pay, สรุปยอด เงินสด/โอน, CSV, ใบเสร็จ, หน้าชำระเงิน, mirror saleRows ที่แปลง method เป็น cash/transfer, qa/mysql.js compare) ให้ไล่หาทุกจุดแล้วทำเป็นรายการก่อนแก้ ห้ามทำให้ข้อมูลเก่าอ่านผิด
- ตั้งค่าวิธีชำระ: บัตร (ค่าธรรมเนียม % ) และแพลตฟอร์ม (ชื่อ GP % VAT ของค่าคอมมิชชัน) 
- ลงบัญชี: บัตร เดบิต 1020 ลูกหนี้บัตร เครดิต 4000/2100 · แพลตฟอร์ม ลูกหนี้แพลตฟอร์ม (บัญชีใหม่ ถามผู้ทำบัญชี) · เงินเข้าธนาคาร: เดบิต 1010 + ค่าธรรมเนียม 6600 (+ภาษีซื้อค่าคอมมิชชัน) เครดิตลูกหนี้ ทำผ่านหน้ายืนยันแบบ PromptPay
- สรุปยอด/เงินทอน/ลิ้นชัก (เฉพาะเงินสดเท่านั้นเข้าลิ้นชัก)
ถามก่อน: อัตราค่าธรรมเนียมต่อบิลหรือต่อรอบ · VAT ของค่าคอมมิชชันแพลตฟอร์มเป็นภาษีซื้อได้หรือไม่ (ผู้ทำบัญชี) · ยอดขายผ่านแพลตฟอร์มรับรู้เต็มจำนวนก่อนหักคอมมิชชัน (แนะนำ)
````

### P15 · พยากรณ์ยอดขายรายเมนู → แนะนำปริมาณสั่งซื้อ

````text
งาน P15: พยากรณ์จำนวนขายรายเมนู แปลงเป็นปริมาณวัตถุดิบที่ควรสั่ง · ต้องมี P4 P6 P9
- วิธีอธิบายได้ ไม่ใช้ไลบรารี/โมเดลทึบ: ค่าเฉลี่ยตามวันในสัปดาห์ย้อนหลัง 8 สัปดาห์ ถ่วงน้ำหนักช่วงล่าสุด + ตัวคูณเหตุการณ์ที่ผู้จัดการใส่เอง (วันหยุด งานในย่าน)
- ปริมาณแนะนำ = ใช้คาดการณ์ในช่วงรอของ (lead time ของผู้ขาย ใส่ในรายชื่อ) + กันชน − คงเหลือ ปัดเป็นหน่วยซื้อ แยกตามผู้ขาย แสดงเหตุผลทุกตัวเลข
- ทดสอบย้อนหลัง (backtest) บนข้อมูล 1 ปีสังเคราะห์ รายงานความคลาดเคลื่อน (MAPE) ในเอกสาร ถ้าแย่กว่า "ใช้ค่าเฉลี่ยวันเดียวกันสัปดาห์ก่อน" ให้ใช้วิธีง่ายกว่า
- ไม่สั่งซื้อให้เอง แค่แนะนำ · งบซื้อเดือนถัดไปเสนอ = ยอดขายคาดการณ์ × เป้าต้นทุนอาหาร (เชื่อม P6)
ถามก่อน: ร้านเปิดไม่ครบสัปดาห์/ปิดวันไหน · กันชนกี่วัน
````

````text
งาน P16: ส่งวัตถุดิบ สูตร ความเคลื่อนไหววัตถุดิบ สมุดรายวัน เจ้าหนี้ ใบรับของ รายจ่าย อนุมัติ ไป MySQL ทางเดียว ตามกฎข้อ 75–80 · ต้องมี P2–P7

ถามก่อน: รายการ ov_ing_moves ละเอียดทุกความเคลื่อนไหวหรือสรุปรายวัน [แนะนำ: ละเอียด]
````

### P17 · หลายสาขา: ส่งออก/นำเข้า cost_master

````text
งาน P17: ใช้สูตรและวัตถุดิบมาตรฐานเดียวกันหลายสาขา โดยไม่มี Cloud กลาง · ต้องมี P3 P4

- ถามก่อน: จะให้ไฟล์เซ็นลายเซ็นไหม (ต้องมีกุญแจร่วม: เสนอ HMAC ด้วยรหัสที่เจ้าของตั้งตอนส่งออกและกรอกตอนนำเข้า ไม่เก็บในไฟล์) · ถ้าต้องการ Cloud HQ จริง ให้หยุดและรายงานว่าขัดกฎข้อ 75 ต้องตัดสินใจเชิงสถาปัตยกรรมก่อน
````

### P18 · ส่งออกให้โปรแกรมบัญชี + ปิดงวดบัญชี

````text
งาน P18: ส่งออกรูปแบบที่โปรแกรมบัญชีนำเข้าได้ และปิดงวด · ต้องมี P2 P8
- ถามผู้ใช้ก่อนว่าผู้ทำบัญชีใช้โปรแกรมอะไร (เช่น FlowAccount, PEAK, Express, Excel) แล้วทำรูปแบบนำเข้าตามที่โปรแกรมนั้นรองรับ ถ้ายังไม่รู้ ทำ CSV สมุดรายวันมาตรฐาน (วันที่ เลขที่ รหัสบัญชี ชื่อบัญชี เดบิต เครดิต คำอธิบาย) ห้ามเดารูปแบบของโปรแกรมที่ไม่มีเอกสาร
- ปิดงวด (เจ้าของ + PIN ซ้ำ + confirmBox): ลงรายการวันที่ในงวดที่ปิดแล้วไม่ได้ (รวมการลงย้อนหลัง/ยกเลิก) · ต้องเปิดงวดใหม่ด้วยรายการกลับพร้อมเหตุผลเท่านั้น (audit) · ปิดงวดสร้างสแนปช็อตยอดคงเหลือต่อบัญชี (ledger/snap-YYYY-MM.json) ใช้เร่งการเปิดระบบ
- ตรวจก่อนปิดงวด: งบทดลองสมดุล · 1200 ตรงสต็อก · ไม่มีรายการรออนุมัติของงวดนั้น · ไม่มีกะค้าง · แสดงผลตรวจให้เห็นก่อนยืนยัน
- เทสต์: ลงบัญชีย้อนเข้างวดปิดถูกปฏิเสธทุกช่องทาง (ขายย้อน ยกเลิก อนุมัติ) · เปิดงวดแล้วทำงานต่อ · กู้คืนข้ามงวด
````

### P19 · ให้ผู้ทำบัญชีตรวจ (พรอมต์สำหรับสร้างเอกสารให้นักบัญชี ไม่ใช่เขียนโค้ด)

````text
งาน P19: เตรียมเอกสารให้ผู้ทำบัญชีของร้านตรวจผังบัญชีและรายงาน VAT ก่อนใช้จริง ห้ามแก้โค้ดในงานนี้
สร้างไฟล์ docs/ACCOUNTANT-REVIEW.md ภาษาไทย อ่านง่ายสำหรับผู้ไม่ใช่โปรแกรมเมอร์ ประกอบด้วย
1) สรุประบบ 1 หน้า: ลงบัญชีอย่างไรจากเหตุการณ์แต่ละแบบ (ตารางเหตุการณ์ → เดบิต/เครดิต) อ่านจากโค้ด lib/ledger.js และตัวลงบัญชีจริง ไม่ใช่จากเอกสาร (ถ้าไม่ตรงกับ ONESTOP-SPEC ให้ชี้ความต่าง)
2) ผังบัญชีทั้งหมดที่ใช้จริง + บัญชีที่เราเพิ่มเอง (ค่าบริการ ลูกหนี้ เงินขาด/เกิน ฯลฯ) พร้อมเหตุผล
3) รายการคำถามที่ต้องให้นักบัญชียืนยัน (ใส่ช่อง ✔/✘/ความเห็น): การรับรู้ค่าบริการ 10% · จุดเกิดภาษีขายของบิลโต๊ะ/ใบแจ้งหนี้ · เงื่อนไขภาษีซื้อและใบกำกับภาษีเต็มรูป และการแยก VAT จากยอดรวม (107) · ต้นทุนเฉลี่ยเคลื่อนที่เหมาะกับร้านหรือไม่ · การรับรู้ต้นทุนตามสูตรเทียบการใช้จริง · เงินขาด/เกินลิ้นชัก · ค่าธรรมเนียมบัตร/แพลตฟอร์มและ VAT ของมัน · รายจ่ายที่ต้องหัก ณ ที่จ่ายหรือประกันสังคมหรือไม่ (ระบบยังไม่รองรับ) · การปิดงวด
4) ตัวอย่างข้อมูล 1 วันจากเดโม (P20) พร้อมสมุดรายวันที่ได้ และงบทดลอง ให้นักบัญชีไล่ด้วยมือได้
5) รายงาน VAT ประมาณการของเดือนตัวอย่างและวิธีคำนวณ
ห้ามอ้างข้อกฎหมายภาษีว่าถูกต้องแน่นอน เขียนเป็น "สิ่งที่ต้องตรวจ" เท่านั้น
````

### P20 · เดโม + ภาพหน้าจอ + คู่มือผู้ใช้

## 6b. เพิ่มจากเมนูที่ผู้ใช้ส่งมา (4 พ.ย. 2569) · P21–P27

ผู้ใช้ส่งโครงเมนูของหน้าพนักงาน 5 กลุ่ม (รับออเดอร์ / เอกสารและภาษี / รายงานและสถิติ / คลังและต้นทุน / จัดการระบบ) มาให้เทียบกับของที่มี รายการที่ **ยังไม่อยู่ใน P1–P20** ถูกเพิ่มเป็น P21–P27 ข้างล่าง ส่วนรายการที่ P1–P20 ครอบอยู่แล้วดูตารางข้อ 3

> **ข้อสมมติที่ใช้ตอนเขียน (ผู้ใช้ยังไม่ได้ตอบ 3 คำถามที่ถามไว้ จึงใส่เป็น "คำถามที่ต้องถามก่อน" ในพรอมต์ให้ AI ถามซ้ำก่อนเขียนโค้ด):**
> 1. ถือว่าเมนูที่ส่งมาคือ **เป้าหมายของระบบนี้** ไม่ใช่เมนูของระบบอื่นที่ใช้อ้างอิง (P21 ถามยืนยันอีกครั้ง)
> 2. "บิลภายใน" ตีความว่าเป็น **การใช้ของภายในร้าน** (อาหารพนักงาน ทดสอบเมนู แจก) ไม่ใช่บิลขายที่ไม่ออกใบกำกับภาษี (P25 ถามยืนยัน ถ้าเป็นอย่างหลังต้องหยุดถามเรื่องภาษี)
> 3. "รายงานประสิทธิภาพ" ยังไม่รู้ว่าวัดอะไร (P27 ให้ถามก่อนเสมอ และชี้ว่าข้อมูลบางอย่างยังไม่ถูกเก็บ)
> 4. "หน้าจอบาร์น่า" ในรายการน่าจะพิมพ์ผิดจาก "บาร์น้ำ" (P21 ถามยืนยัน)

**ลำดับที่แนะนำ:** P21 (จัดเมนูเป็นกลุ่ม) ทำ **หลัง P1 ก่อน P2** เพื่อให้หน้าจอใหม่ทุกขั้นอยู่ถูกกลุ่มตั้งแต่แรก · P22 ทำเมื่อไรก็ได้ (ไม่พึ่งต้นทุน) · P23 หลัง P8 และต้องให้ผู้ทำบัญชีตอบก่อน · P24 หลัง P14 · P25 หลัง P5 · P26 หลัง P13 · P27 ทำเมื่อไรก็ได้ แต่ควรเริ่มเก็บข้อมูลเวลา/ผู้รับเงินให้เร็ว เพราะข้อมูลที่ไม่เคยเก็บย้อนหลังไม่ได้

### P21 · จัดเมนูเป็นกลุ่ม (กลุ่ม › รายการ)

````text
งาน P21: จัดเมนูหน้าพนักงานเป็นกลุ่มตามเมนูที่ผู้ใช้ส่งมา โดยไม่ทำให้สคริปต์ QA และพฤติกรรมเดิมพัง

เมนูเป้าหมาย (กลุ่ม › รายการ)
- รับออเดอร์ › แคชเชียร์ · หน้าจอครัว · หน้าจอบาร์น้ำ
- เอกสารและภาษี › ประวัติใบเสร็จ · ประวัติบิลเงินสด · ออเดอร์เดลิเวอรี · ใบกำกับภาษี · บิลภายใน (+ เอกสารเดิม: ใบเสนอราคา ใบแจ้งหนี้ ใบสั่งซื้อ)
- รายงานและสถิติ › ภาพรวมแดชบอร์ด · รายงานประสิทธิภาพ · ประวัติเข้า-ออกกะแคชเชียร์ · ดาวน์โหลดรายงาน
- คลังและต้นทุน › คลังและสต็อกคงเหลือ · รับสินค้าเข้า · เบิกสินค้าไปใช้ · แปรรูปและชำแหละ · สูตรเมนูอาหาร · ตัดของเสียและชำรุด · ตรวจนับสต็อกจริง · จัดการวัตถุดิบและผู้จำหน่าย
- จัดการระบบ › จัดการร้าน · ผู้ใช้และสิทธิ์

ปัจจุบัน: แท็บแนวนอน (kitchen tables counter docs stock menu report settings) ผ่าน allowedTabs()/TABS ตามบทบาท × วิธีขาย · จอ ≥ 1024px แท็บเป็นแถบซ้ายด้วย CSS อยู่แล้ว

สร้าง
1) ชั้นนำทาง 2 ระดับ กลุ่ม › รายการ โดยรายการหนึ่งชี้ไปที่ (tab, มุมมองย่อย) ของแท็บที่มีอยู่ เช่น "หน้าจอบาร์น้ำ" = แท็บครัวพร้อมตัวกรองจุด bar · "แคชเชียร์" = แท็บขายหน้าร้าน (ร้านที่เปิดโต๊ะมี "โต๊ะ & บิล" ด้วย) · "ดาวน์โหลดรายงาน" = ส่วนส่งออกของแท็บสรุปยอด · ทำ "ตารางแมป" (รายการ → tab + sub + สิทธิ์บทบาท + วิธีขายที่ต้องเปิด) ไว้ที่เดียวในโค้ดและลง AGENTS.md
2) ห้ามเปลี่ยน/ลบ data-v ของปุ่มแท็บเดิม และห้ามเปลี่ยน id/selector ที่ qa/ ใช้ (#tabs .tab, #tabs [data-v=...], #v-<tab>) กลุ่มเป็นชั้นแสดงผลทับ: หัวกลุ่มยุบ/ขยายได้ (จำค่าใน localStorage) กลุ่มที่ไม่มีรายการให้บทบาทนั้น/วิธีขายนั้น ไม่แสดง
3) รายการของพรอมต์ที่ยังไม่ได้ทำ (สูตรเมนูอาหาร ตรวจนับ ฯลฯ) แสดงเมื่อหน้านั้นมีจริงและเปิดโหมดที่เกี่ยวข้องเท่านั้น ห้ามมีเมนูตายที่กดแล้วไม่มีอะไร
4) มือถือ: เมนูกลุ่มแนวตั้ง/ลิ้นชัก ปุ่ม ≥ 44px ไม่ล้นจอที่ 320px ใช้คีย์บอร์ดและ screen reader ได้ (aria-expanded ลำดับโฟกัส)
5) ลิงก์ลึก: เก็บ tab + sub ใน location.hash ให้ปุ่มย้อนกลับของเบราว์เซอร์และการรีเฟรชกลับมาหน้าเดิม
6) บทบาท: คนที่ไม่มีสิทธิ์ไม่เห็นรายการ (ซ่อนเพื่อความสะดวก) ความปลอดภัยยังตรวจที่เซิร์ฟเวอร์ตามกฎข้อ 34 เหมือนเดิม

คำถามที่ต้องถามก่อน
1. เมนูที่ส่งมา "ไม่มีกลุ่มบัญชี" แต่งานของเรามี (สมุดรายวัน บันทึกรายจ่าย/รายรับ กำไรขาดทุน ภาษี เจ้าหนี้ ใน P2–P8): (ก) เพิ่มกลุ่ม "บัญชี" ระหว่างคลังและต้นทุนกับจัดการระบบ [แนะนำ] (ข) ฝากไว้ใน "รายงานและสถิติ"
2. เมนูที่ส่งมาเป็นเป้าหมายของระบบเรา หรือเป็นเมนูของระบบอื่นที่ใช้อ้างอิง (ถ้าอ้างอิง ให้เลือกเฉพาะรายการที่ร้านใช้จริง)
3. ลิงก์ลึกผ่าน hash ทำไหม [แนะนำ: ทำ]
4. "หน้าจอบาร์น่า" ในรายการ น่าจะคือ "บาร์น้ำ" ยืนยัน

เทสต์ที่ต้องมี: qa/browser.js ทุกเคสเดิมผ่านโดยไม่แก้ selector · เคสใหม่ nav: ทุกบทบาท × ทุกวิธีขาย รายการที่เห็น = ตารางแมป · กลุ่มว่างไม่แสดง · ยุบ/ขยายจำค่า · hash กับปุ่มย้อนกลับ · 320/390/1440px ไม่ล้นจอ · a11y.js 0 ปัญหา light/dark · ใช้คีย์บอร์ดอย่างเดียวได้
เสร็จเมื่อ: เมนูเป็นกลุ่มตามที่ส่งมา สคริปต์ QA เดิมทั้งหมดผ่านโดยไม่แก้ selector
````

### P22 · หน้าค้นประวัติใบเสร็จและบิลเงินสด

````text
งาน P22: หน้าค้นและพิมพ์ซ้ำใบเสร็จ/บิลย้อนหลังทุกเดือน (ตอนนี้เห็นแค่บิลวันนี้จาก GET /api/report และ CSV รายเดือน)

ข้อมูล: sales/YYYY-MM.jsonl (ทุกบิลถาวร) และ D.sales (8 วันล่าสุด) · บิลมี no at table items sub svc vat total method kind level memo q doc disc (และ cogs ถ้ามี P4) · เลขบิลแสดง R<yyyymmdd>-<no> (billNo())

สร้าง
1) GET /api/sales?month=YYYY-MM&q=&method=&kind=&table=&min=&max=&page= (FRONT + MGR): อ่านไฟล์เดือนนั้นแบบ stream/async (กฎข้อ 33 ห้ามอ่านทั้งไฟล์แบบ sync) · ค้นด้วยเลขบิล (R...-0012 หรือ 12) ชื่อสินค้าในบิล หมายเหตุ ช่วงยอด โต๊ะ/คิว วิธีชำระ ประเภท (ขาย/รับซื้อ) · แบ่งหน้า ≤ 100 · เรียงใหม่→เก่า · ผลรวมของที่ค้นเจอ (จำนวนบิล ยอดรวม) · ข้อมูลเป็นหมื่นบิลต่อเดือนต้องไม่ทำให้ event loop ค้าง (วัดด้วย qa/perf.js)
2) GET /api/sale?no= บิลหนึ่งใบข้อมูลครบสำหรับพิมพ์ซ้ำ · พิมพ์ซ้ำด้วย printMode('receipt') เดิม ใช้ค่าที่บันทึกในบิล ไม่เขียนสูตรเงินใหม่ · ใบที่พิมพ์ซ้ำต้องมีคำว่า "สำเนา" พร้อมเวลาพิมพ์ กันเอาไปใช้เป็นต้นฉบับซ้ำ
3) สองหน้าตามเมนู: "ประวัติใบเสร็จ" (ทุกบิลขาย) และ "ประวัติบิลเงินสด" (กรองเงินสด + ผลรวมเงินสดรายวันไว้เทียบกับลิ้นชัก) ใช้ฟังก์ชันค้นเดียวกัน ห้ามทำสองชุด
4) พนักงานเสิร์ฟและครัวไม่เห็น · พิมพ์ซ้ำบันทึก audit (เลขบิล ผู้พิมพ์) ไม่เก็บข้อมูลส่วนตัวของลูกค้า
5) ส่งออก CSV ของผลที่ค้นเจอ (BOM ผ่าน q() กฎข้อ 14/25)

คำถามที่ต้องถามก่อน
1. ย้อนหลังได้ไกลแค่ไหน [แนะนำ: ทุกเดือนที่มีไฟล์ใน sales/]
2. พิมพ์ซ้ำเป็น "สำเนา" ไหม [แนะนำ: ใช่]
3. แคชเชียร์ค้นบิลเกิน 8 วันได้ไหม [แนะนำ: ได้ เฉพาะดู/พิมพ์ซ้ำ ไม่มีแก้ไข]
4. คืนเงิน/ยกเลิกบิลที่ปิดแล้วยังไม่มีในระบบ (ข้อจำกัดข้อ 10) พรอมต์นี้ไม่ทำ ห้ามมีปุ่มที่ทำท่าว่าทำได้

เทสต์ที่ต้องมี: ผลค้น = ข้อมูลดิบในไฟล์ทุกฟิลด์ (เทียบอิสระ) · ไฟล์ที่มีบางบรรทัดเสียไม่ล้ม · เดือนไม่มีไฟล์ = ว่าง · สิทธิ์ทุกบทบาท · event loop lag ไม่เกินเกณฑ์กับข้อมูล 1 ปี · CSV injection · พิมพ์ซ้ำยอดตรงบิลเดิมทุกสตางค์ (qa/browser.js เคส print เป็น PDF 80 มม.) · a11y
เสร็จเมื่อ: ค้นบิลของ 3 เดือนก่อนด้วยเลขบิลแล้วพิมพ์ซ้ำได้ยอดตรง
````

### P23 · ใบกำกับภาษีเต็มรูป (ต้องให้ผู้ทำบัญชีตอบก่อน)

````text
งาน P23: ออกใบกำกับภาษีเต็มรูปให้ลูกค้าที่ขอ จากบิลขายที่มีอยู่ (ตอนนี้มีแต่ใบแจ้งหนี้ของร้านจด VAT ที่ใช้หัว "ใบส่งของ/ใบแจ้งหนี้/ใบกำกับภาษี" ใบกำกับภาษีเต็มรูปจากบิลขายหน้าร้านและโหมดราคารวม VAT ยังไม่มี ดู AGENTS ข้อ 10)

⚠ เรื่องภาษี ห้ามตัดสินรายละเอียดเอง ทุกข้อใน "ถามก่อน" ต้องให้ผู้ทำบัญชียืนยันก่อนเขียนโค้ด และบันทึกคำตอบลง QA-LOG ข้อ 6 · งานนี้ต้องทำหลัง P8 (รายงาน VAT) เพื่อให้ตัวเลขภาษีขายตรงกัน

สร้าง (หลังผู้ทำบัญชียืนยัน)
1) ประเภทเอกสารใหม่ TX ใบกำกับภาษี (เลข TX2026-0001 เรียงต่อเนื่อง ห้ามย้อน/ซ้ำ ผ่าน nextDocNo/docChanged/journal เดิม ตามวิธี "ประเภทเอกสารใหม่" ใน AGENTS ข้อ 7) ผูกกับบิลขายเลขเดียว (1 บิลต่อ 1 ใบ ซ้ำไม่ได้) ดึงรายการ ยอด ภาษี จากบิลจริงที่เซิร์ฟเวอร์ ห้ามให้พิมพ์ยอดเอง
2) ข้อมูลผู้ซื้อ: ชื่อ ที่อยู่ เลขผู้เสียภาษี 13 หลัก สาขา (ตรวจรูปแบบเหมือนรายชื่อลูกค้าเดิม) ข้อมูลผู้ขายจากตั้งค่า ร้านที่ไม่มีเลขผู้เสียภาษีหรือไม่จด VAT = ออกไม่ได้ (ข้อความไทยบอกชัด)
3) กระดาษ A4 (docPaper) หัวและช่องที่ต้องมีตามที่ผู้ทำบัญชียืนยัน · จำนวนเงินเป็นตัวหนังสือ (bahtText เดิม) · ต้นฉบับ/สำเนา
4) ยกเลิก: ห้ามลบ ห้ามแก้ · วิธียกเลิก (ใบยกเลิก/ใบลดหนี้) ตามที่ผู้ทำบัญชียืนยัน ระบบยังไม่มีใบลดหนี้ ต้องมีเหตุผลและ confirmBox เลขที่ที่ยกเลิกแล้วไม่ถูกนำกลับมาใช้ (กฎข้อ 69)
5) ลงรายงาน VAT (P8) ให้ตรงกับบิลต้นทางทุกสตางค์ ไม่นับซ้ำ (บิลหนึ่งใบเป็นทั้งใบเสร็จและมีใบกำกับภาษี = ภาษีขายครั้งเดียว)
6) สิทธิ์: FRONT + MGR ออกได้ · ยกเลิกเฉพาะเจ้าของ · audit ทุกครั้ง

ถามก่อน (ผู้ทำบัญชีต้องตอบ)
1. ใบกำกับภาษีเต็มรูปจากบิลที่ออกใบเสร็จไปแล้ว: เลขที่แยกต่อเนื่องจากใบเสร็จหรือไม่ ต้องมีข้อความอะไรบนกระดาษบ้าง
2. ใบกำกับภาษีอย่างย่อสำหรับลูกค้าทั่วไป ต้องทำด้วยไหม ใบเสร็จปัจจุบันใช้แทนได้หรือไม่ ต้องเพิ่มอะไร
3. ลูกค้าขอใบเต็มรูปหลังจ่ายแล้วข้ามวัน/ข้ามเดือน ออกได้ภายในกี่วัน
4. ระบบเดิมคิด VAT เพิ่มจากราคา (ไม่ใช่ราคารวม VAT) ร้านนี้ต้องใช้แบบไหน ถ้าต้องรวม VAT ให้แยกเป็นงานต่างหากก่อน เพราะกระทบ store.totals() calc() posTotals() docTotals() ทุกที่
5. วิธียกเลิกใบกำกับภาษีที่ออกแล้ว (ต้องมีใบลดหนี้ไหม)

เทสต์ที่ต้องมี: 1 บิลต่อ 1 ใบ · ยอด/ภาษีตรงบิลต้นทาง (สุ่ม ≥ 3,000 บิล) · เลขต่อเนื่องไม่ซ้ำไม่ย้อน แม้ kill -9/กู้คืน · เลขผู้เสียภาษีผิดรูปแบบถูกปฏิเสธ · ร้านไม่จด VAT ออกไม่ได้ · รายงาน VAT ไม่นับซ้ำ · PDF A4 หนึ่งหน้า
เสร็จเมื่อ: ผู้ทำบัญชีตรวจตัวอย่าง PDF และยืนยันเป็นลายลักษณ์อักษร (บันทึกใน QA-LOG)
````

### P24 · ออเดอร์เดลิเวอรี (ทะเบียนบิล)

````text
งาน P24: ทะเบียนออเดอร์เดลิเวอรี (Grab, LINE MAN, ShopeeFood, โทรสั่ง ฯลฯ) · ต้องมี P14 (วิธีชำระแบบแพลตฟอร์ม) ถ้าเปิดโหมด cost · ถ้ายังไม่เปิด cost ให้ทำเวอร์ชันบันทึกยอดอย่างเดียว

บริบท: ในเมนูที่ผู้ใช้ส่งมา "ออเดอร์เดลิเวอรี" อยู่ในกลุ่ม "เอกสารและภาษี" แปลว่าน่าจะเป็นทะเบียนบิล ไม่ใช่หน้ารับออเดอร์จากแอป · ห้ามเชื่อม API ของแพลตฟอร์ม (ไม่มี dependency ระบบต้องทำงานตอนเน็ตดับ)

สร้าง
1) ออเดอร์เดลิเวอรี = บิลขายชนิดหนึ่ง (ใช้ POST /api/sale เดิมหรือต่อยอด ห้ามทำเส้นทางเงินใหม่ที่ขนานกัน): แหล่งที่มา (ชื่อแพลตฟอร์มจากรายการที่เจ้าของตั้ง) เลขออเดอร์ของแพลตฟอร์ม ชื่อ/เบอร์ลูกค้า (ไม่บังคับ) ค่าส่ง ค่าคอมมิชชัน (% หรือบาท) ยอดที่แพลตฟอร์มจะโอนให้ร้าน เวลา สถานะ (รอทำ/ส่งแล้ว/ยกเลิก)
2) ส่งเข้าจอครัว/บาร์เป็นคิวได้ ใช้ตั๋ว table 0 เดิม (กฎข้อ 59) พร้อมป้ายแพลตฟอร์มบนตั๋ว
3) เงิน: แพลตฟอร์มโอนทีหลัง จึงไม่เข้าเงินสดในลิ้นชัก ไม่ทำให้เงินทอน/ปิดกะเพี้ยน · ยอดขายรับรู้เต็มจำนวนก่อนหักคอมมิชชัน (ตามคำตอบ P14) · เมื่อแพลตฟอร์มโอนเข้าธนาคาร ผู้จัดการกด "ยืนยันรับเงิน" แบบเดียวกับ PromptPay (P11/P14) คอมมิชชันลงบัญชี 6600 ไม่ทำให้ยอดขายเพี้ยน
4) หน้า "ออเดอร์เดลิเวอรี" (FRONT + MGR): รายการตามช่วงวัน กรองตามแพลตฟอร์ม/สถานะ ยอดค้างรอโอนแยกต่อแพลตฟอร์ม ส่งออก CSV
5) ถ้าเพิ่มฟิลด์ใน sales (platform platformNo commission) ต้องผ่าน normalize (ไฟล์เดิมไม่มีฟิลด์ต้องอ่านได้) saleRows() ของ mirror (SCHEMA ใหม่ + ALTER ตามกฎข้อ 80) และ qa/mysql.js

ถามก่อน
1. ยืนยันว่าเป็น "ทะเบียนบิลเดลิเวอรีที่บันทึกด้วยมือ" ไม่ใช่เชื่อม API [แนะนำ]
2. ค่าคอมมิชชันใส่เป็น % หรือยอดจริงตามรายงานแพลตฟอร์ม [แนะนำ: ได้ทั้งสองแบบ ยอดจริงทับ %]
3. VAT ของค่าคอมมิชชัน (ภาษีซื้อ) ทำอย่างไร (ผู้ทำบัญชีตอบ)
4. ออเดอร์ที่ยกเลิกหลังครัวเริ่มทำ = ของเสียอัตโนมัติ (P5) ไหม [แนะนำ: ใช่ ผ่านกลไกเดิม]

เทสต์ที่ต้องมี: บิลเดลิเวอรีไม่เข้าเงินสดลิ้นชัก · ยอดขายรายวัน/สรุปยอด/CSV/งบทดลองตรงกันทุกสตางค์ · ยืนยันรับเงินแล้วยอดค้างลด · ยกเลิก · ตั๋วคิวเข้าจอครัวพร้อมป้าย · ไฟล์เก่าที่ไม่มีฟิลด์ใหม่ยังอ่านได้ (upgrade.js)
เสร็จเมื่อ: บันทึกออเดอร์ Grab 5 บิล ยอดค้างรอโอนตรงกับผลรวม ยืนยันรับเงินแล้วบัญชีสมดุล
````

### P25 · เบิกใช้ภายในและบิลภายใน

````text
งาน P25: ของที่ใช้ภายในร้านโดยไม่ได้ขายให้ลูกค้า มี 2 ทาง: (ก) "เบิกสินค้าไปใช้" ตัดวัตถุดิบโดยตรง (ข) "บิลภายใน" ตัดวัตถุดิบตามสูตรของเมนูที่ทำให้คนในร้านกิน/ทดสอบ/แจก · ต้องมี P3 P4 P5 (และ P2 ถ้าเปิดสมุดบัญชี)

สถานะเดิม: มีใบเบิกออก (OUT) ของสินค้าขายตรงในแท็บสต็อก (เจ้าของเท่านั้น ต้องมีเหตุผล) ยังไม่มีสำหรับวัตถุดิบ และ P5 มีเหตุผลของเสีย "อาหารพนักงาน" ซ้อนกับงานนี้ ต้องตัดสินให้ชัดว่าอะไรอยู่ที่ไหน (ถามข้อ 2)

สร้าง
1) เบิกวัตถุดิบไปใช้: POST /api/ing/issue {lines:[{ing, qty}], purpose, note} สิทธิ์ทุกบทบาทยกเว้นพนักงานเสิร์ฟ · purpose จากรายการคงที่ (ใช้ในครัว/ทดสอบสูตร/อาหารพนักงาน/ตัวอย่างลูกค้า/แจก-โปรโมชัน/โอนไปสาขาอื่น) · ingMove kind 'issue' มูลค่า = ทุนเฉลี่ย · ลงบัญชีเดบิตบัญชีค่าใช้จ่ายตาม purpose เครดิต 1200 (ไม่ใช่ 5000/5100 เพื่อไม่ปนกับ food cost ของที่ขายจริง ถามข้อ 3) · มูลค่า ≥ wasteAck เข้าคิวรับทราบ (ack) เหมือนของเสีย
2) บิลภายใน: เลือกเมนู จำนวน ผู้ใช้/เหตุผล · ไม่มีรายได้ ไม่เข้ายอดขาย ไม่เข้าสรุปยอด (kind 'internal' ตามกฎข้อ 58: ทุกที่ที่รวมยอดขายต้องแยกออก) · ตัดวัตถุดิบตามสูตร (recipeUsage) ต้นทุนบันทึกที่บิล · เลขที่ IB2026-0001 ต่อเนื่องไม่ย้อน (ผ่าน docSeq/docChanged เดิม ถามข้อ 4) · ยกเลิกต้องมีเหตุผล + ingMove กลับ + ลงบัญชีกลับ
3) หน้า "เบิกสินค้าไปใช้" (กลุ่มคลังและต้นทุน) และ "บิลภายใน" (กลุ่มเอกสารและภาษี) ตาม P21 · ผู้เบิกไม่เห็นทุน (กฎปกปิดของ P3) · รายงานรวมค่าใช้ภายในต่อเดือนต่อ purpose (MGR) เข้า P&L เป็นบรรทัดแยก
4) บัญชีที่ใช้และการรับรู้ (สวัสดิการ/ค่ารับรอง/ส่งเสริมการขาย) ต้องให้ผู้ทำบัญชียืนยัน

ถามก่อน
1. "บิลภายใน" หมายถึงอะไร: (ก) การใช้ของภายในร้าน อาหารพนักงาน/ทดสอบ/แจก [แนะนำ ตามข้างบน] (ข) บิลขายที่ไม่ออกใบกำกับภาษี (ค) อย่างอื่น · ถ้าเป็น (ข) หยุดและรายงาน เพราะต้องตัดสินเรื่องภาษีก่อน
2. อาหารพนักงาน: ย้ายจากเหตุผลของเสีย (P5) มาอยู่ที่งานนี้ทั้งหมด [แนะนำ: ใช่ ของเสียจริงจะได้ไม่ปนกับอาหารพนักงาน] ถ้าย้ายต้องแก้ P5 และเทสต์ที่เกี่ยวข้อง
3. บัญชีค่าใช้จ่ายของแต่ละ purpose: เสนอ 6200 สวัสดิการพนักงาน · 6500 การตลาด/โปรโมชัน · 6900 อื่นๆ (ผู้ทำบัญชียืนยัน)
4. เลขที่บิลภายใน: [แนะนำ: ประเภทเอกสารใหม่ IB ใน docSeq ได้ rev/ยกเลิก/journal ฟรี]
5. บิลภายในที่คิดราคา > 0 (หักเงินเดือนพนักงาน) อยู่นอกขอบเขต [แนะนำ]

เทสต์ที่ต้องมี: บิลภายในไม่เข้ายอดขาย/CSV ยอดขาย/popularIds()/KPI food cost (สแกนทุกที่ที่รวม sales) · 1200 = Σ มูลค่าวัตถุดิบ หลังเบิก/บิลภายใน/ยกเลิก · เบิกเกินคงเหลือ (ติดลบ) ทำงานตามกฎติดลบ · ผู้เบิกไม่เห็นทุน · สุ่ม ≥ 3,000 รายการ ΣDr=ΣCr · kill -9
เสร็จเมื่อ: เบิกวัตถุดิบ 3 ครั้งต่างเหตุผลและทำบิลภายใน 2 ใบ รายงานค่าใช้ภายในตรงกับสมุดบัญชีทุกสตางค์ และ food cost % ไม่เปลี่ยน
````

### P26 · แปรรูปและชำแหละ

````text
งาน P26: แปรรูปวัตถุดิบชิ้นใหญ่เป็นหลายชิ้น (หมูทั้งตัว/สามชั้นทั้งแผ่น ปลาทั้งตัว ไก่ทั้งตัว หั่นแล่ ฯลฯ) พร้อมแบ่งต้นทุนไปยังชิ้นที่ได้ · ต้องมี P3 P5 (ทำหลัง P13 จะใช้เครื่องยนต์ "แปลงสต็อก" ร่วมกันได้)

ต่างจาก P13: P13 = หลายวัตถุดิบเข้า ได้ของเตรียม 1 อย่างตามสูตร (น้ำซุป ซอส) · P26 = วัตถุดิบ 1 อย่างเข้า ได้หลายอย่างออก (ชิ้นเนื้อ กระดูก หนัง เศษ) น้ำหนักแต่ละชิ้นชั่งจริงทุกครั้ง

สร้าง
1) POST /api/ing/convert {from:{ing, qty}, outputs:[{ing, qty, share?}], loss, note} สิทธิ์ MGR และครัว (ครัวทำได้ ไม่เห็นทุน) · ingMove 'break-out' ตัดต้นทาง ณ ทุนเฉลี่ย และ 'break-in' เพิ่มปลายทางด้วยมูลค่าที่แบ่งให้ · Σ มูลค่าปลายทาง + มูลค่าส่วนสูญเสีย = มูลค่าที่ตัดออกเป๊ะ (สตางค์จำนวนเต็ม แบ่งเศษด้วย largest remainder) จึงไม่กระทบ P&L ยกเว้นส่วนสูญเสียที่เกินเกณฑ์ → ของเสีย 5100
2) การแบ่งต้นทุนต่อชิ้น: ตามน้ำหนัก (ค่าตั้งต้น) หรือตามสัดส่วนมูลค่าตลาดที่ผู้จัดการตั้งต่อชิ้น (share) พลอยได้ (กระดูก เศษ) ตั้ง share 0 ได้ · แม่แบบการแปรรูป (ต้นทาง → ชิ้นที่คาดว่าจะได้ + % ผลได้ที่คาด) ระบบเทียบผลได้จริงกับที่คาด เตือนผู้จัดการเมื่อต่ำกว่าเกณฑ์ (ไม่หยุดงาน)
3) ผลได้ที่วัดจริงทำให้ทุนต่อหน่วยของชิ้นที่ได้สูงกว่าทุนต้นทางตามธรรมชาติ ใช้ต้นทุนเฉลี่ยเคลื่อนที่ของ P3 เหมือนเดิม
4) หน้า "แปรรูปและชำแหละ" ใช้บนมือถือได้ (ครัวชั่งแล้วกรอกที่หน้างาน) ช่องตัวเลขห้ามถูกวาดทับระหว่างพิมพ์ (กฎข้อ 32) ตรวจ Σ น้ำหนักออก + สูญเสีย = น้ำหนักเข้า ไม่ตรงตามเกณฑ์ = ถามยืนยันก่อนบันทึก
5) ยกเลิกรายการ (MGR + เหตุผล + confirmBox): ingMove กลับ ถ้าชิ้นที่ได้ถูกใช้ไปแล้วต้องแสดงผลต่อทุนก่อนยืนยัน

ถามก่อน
1. แบ่งต้นทุนตามน้ำหนัก หรือตามมูลค่าตลาด [แนะนำ: เริ่มตามน้ำหนัก มีช่อง share ให้ผู้จัดการปรับ]
2. ส่วนสูญเสียที่อยู่ในเกณฑ์ที่คาด รวมในต้นทุนชิ้นที่ได้ ส่วนที่เกินเกณฑ์เป็นของเสีย (5100) [แนะนำ] หรือถือเป็นของเสียทั้งหมด
3. แปรรูปหลายขั้น (หมูทั้งตัว → สามชั้นแผ่น → สามชั้นหั่น) [แนะนำ: ได้ แต่ห้ามวนกลับ ตรวจรอบ]

เทสต์ที่ต้องมี: Σ มูลค่าออก = มูลค่าเข้า ทุกกรณี (สุ่ม ≥ 5,000 ชุด รวมเศษสตางค์ น้ำหนักทศนิยม สูญเสีย 0 และ 100%) · 1200 ตรงหลังแปรรูป/ยกเลิก/kill -9 · ผลได้ต่ำกว่าเกณฑ์เตือน · ครัวไม่เห็นทุน · วนกลับถูกปฏิเสธ
````

